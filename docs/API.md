# Swahn Chat API (v1)

This document is the contract between the backend (`backend/`) and the Android client (`android/`).
The running server also serves a generated OpenAPI document at `/api/v1/openapi.json` and Swagger UI at
`/api/v1/docs` (disabled when `SWAHNCHAT_ENV=production` unless `SWAHNCHAT_EXPOSE_DOCS=true`).

## Conventions

- Base path: `/api/v1`. JSON bodies are UTF-8, `snake_case`.
- IDs are UUIDv4 strings (lowercase, with dashes). Message IDs are generated by the client.
- Times are integers: **milliseconds since the Unix epoch, UTC** (`*_at`, `*_ts` fields).
- Binary values in JSON (keys, ciphertext) are **standard base64 with padding**.
- Authentication: `Authorization: Bearer <access_token>` on every endpoint except `/auth/*` (other than
  logout), `/healthz` and `/readyz`.
- Errors: non-2xx responses have the body `{"code": "<machine_code>", "message": "<human text>"}`, sometimes
  with extra fields (documented per endpoint) and, from this version on, `"request_id"` (see below). Common codes:
  `invalid_request` (422), `unauthorized` (401), `token_expired` (401), `forbidden` (403), `not_found` (404),
  `conflict` (409), `rate_limited` (429, with a `Retry-After` header in seconds), `payload_too_large` (413),
  `quota_exceeded` (413), `unsupported_media_type` (415). `403 account_suspended` is returned for every
  authenticated request, login and token refresh of a suspended account (see "Administration").
- Request IDs: every response carries `X-Request-ID`. A client may send its own (`^[A-Za-z0-9._-]{8,64}$`, anything
  else is ignored and replaced); the server uses it in every log line of that request and puts it in error bodies as
  `request_id`, so a user can quote it to the administrator. Clients ignore the field if they do not know it.
- OpenAPI: every operation has a tag, a summary and its error responses (`401`/`403`/`404`/`409`/`413`/`422`/`429` as
  applicable, all with the `{"code","message"}` model). Unknown JSON fields in responses must be ignored by clients:
  new fields are only ever added.
- Response headers: every response carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
  `X-Frame-Options: DENY`, `Permissions-Policy`, `Cross-Origin-Resource-Policy: same-site` and
  `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` (the Swagger UI page at `/api/v1/docs` gets a
  relaxed policy that allows its CDN assets). API responses are `Cache-Control: no-store` unless a route sets its own
  (attachment downloads: `private, no-store`). `Strict-Transport-Security` is sent only when the administrator sets
  `SWAHNCHAT_HSTS=true` (HTTPS only). Clients can ignore all of these.
- Ordering: `seq` values are integers assigned by the server from one monotonic counter. Message `seq` orders
  messages; event `seq` is the sync cursor. They are different counters.

## Objects

```jsonc
// User
{"id": "uuid", "username": "anna", "display_name": "Anna", "avatar_attachment_id": "uuid|null",
 "is_admin": false, "created_at": 1700000000000}

// Device
{"id": "uuid", "user_id": "uuid", "number": 1, "name": "Pixel 8", "created_at": 0, "last_seen_at": 0,
 "identity_key": "base64|null"}   // identity_key is null until the device uploaded keys

// Conversation
{"id": "uuid", "type": "direct|group", "name": "string|null", "avatar_attachment_id": "uuid|null",
 "created_by": "uuid", "created_at": 0, "updated_at": 0, "last_message_at": 0 /*or null*/,
 "last_message_seq": 0 /*or null*/, "disappearing_seconds": 3600 /*or null: server pruning timer, see below*/,
 "my_read_seq": 0, "unread_count": 0,
 "members": [{"user_id": "uuid", "role": "admin|member", "joined_at": 0}]}

// Envelope: one ciphertext addressed to one device
{"device_id": "uuid", "type": "prekey|whisper", "body": "base64"}

// Message (as returned to one device; `envelope` is that device's ciphertext, or null)
{"id": "uuid", "conversation_id": "uuid", "sender_user_id": "uuid", "sender_device_id": "uuid",
 "kind": "message|edit|delete|reaction", "target_message_id": "uuid|null", "client_ts": 0, "server_ts": 0,
 "seq": 0, "attachment_ids": ["uuid"], "deleted": false, "expires_at": 0 /*or null: server pruning time*/,
 "envelope": {"type": "prekey|whisper", "body": "base64"}}
```

`direct` conversations have exactly two members and `name: null`; the client shows the other person's name.

Clients identify devices by `id`. `Device.number` and `device_number` in key bundles are informational only.
All sender, conversation and target fields on message events are claims that clients check against the decrypted
content (see SECURITY.md, "Content is bound to its context").

## Authentication

Accounts exist only through invitations made by an administrator. There is no open signup.

Username: `^[a-z0-9_.-]{3,32}$` (the server lowercases input). Password: 10–256 characters.
Display name: 1–64 characters. Device name: 1–64 characters.

`AuthResponse`:
```json
{"access_token": "jwt", "access_expires_at": 0, "refresh_token": "opaque", "refresh_expires_at": 0,
 "user": {"...User"}, "device": {"...Device"}}
```

| Method | Path | Body | Result |
|---|---|---|---|
| POST | `/auth/invite/redeem` | `{code, username, password, display_name, device_name}` | `201 AuthResponse`. `404 invalid_invite` for unknown/expired/used codes, `409 username_taken` |
| POST | `/auth/login` | `{username, password, device_name}` | `200 AuthResponse`. Every login registers a **new device**. `401 invalid_credentials` (same answer for unknown user and wrong password). `403 account_suspended` when the password is right but the account is suspended (never for a wrong password, so it reveals nothing about usernames). `409 device_limit` when the account already has the maximum number of active devices (default 10, `SWAHNCHAT_MAX_DEVICES_PER_USER`; the `message` says so: remove a device, then log in again). `429 rate_limited` while the username is locked after repeated failures (see below) |
| POST | `/auth/refresh` | `{refresh_token}` | `200 AuthResponse` with a **new** refresh token (`403 account_suspended` while the account is suspended; the session is kept and works again after unsuspending); the old one stops working. Presenting **any** refresh token the session issued earlier (not only the previous one) revokes the whole session and its device (`401 token_reused`) |
| POST | `/auth/logout` | – (auth) | `204`. Revokes the session and the device, deletes the device's public keys |
| POST | `/auth/password/reset` | `{code, new_password, device_name}` | `200 AuthResponse`. Redeems a reset code an administrator issued (see below). `404 invalid_reset_code` for unknown, expired, used or replaced codes (or a removed account), `422` for a weak password, `429` like redeem |

- Access tokens are JWT (HS256) valid for 15 minutes (`SWAHNCHAT_ACCESS_TOKEN_MINUTES`). Refresh tokens are
  random 256-bit values, stored hashed, valid for 60 days (`SWAHNCHAT_REFRESH_TOKEN_DAYS`), sliding on refresh.
- Each request re-checks that the session, device and user are still active, so revocation is immediate.
- An expired access token returns `401 {"code":"token_expired"}`; the client refreshes and retries once.
- Rate limits (in-process): per client IP (IPv6 clients per /64 prefix) login 10/min and 5/min per IP+username,
  redeem 10/min, refresh 30/min; key-bundle fetches 120/min per user. Exceeding returns `429` with `Retry-After`.
- Password reset: an administrator issues a code (`POST /admin/users/{user_id}/password-reset`, or
  `python -m app.cli reset-password <username>` on the server) and hands it to the user over a channel they trust.
  The code has the format of an invitation code, works once, is valid for 24 hours and is stored hashed; issuing a
  new code for the same user cancels the older ones. Redeeming it sets the new password, **revokes every session and
  device of that user** (their public keys and queued messages are deleted, their WebSockets are closed, everyone
  sharing a conversation gets `devices_changed`) and signs the caller in on a **new device** with new keys. Contacts
  therefore see a "new device" notice for this person; that is intended. Messages already on the old phones stay
  readable there but the phones are signed out. Rate limit: 10 per minute per client address, like redeem.
- Per-username lockout: after 10 failed logins within an hour (or 30 within a day) for a username, from any
  addresses, further logins for that username get `429 rate_limited` (with `Retry-After`) until the failures age
  out, even with the right password. Unknown usernames behave identically. Signed-in devices are not affected.
  The failures are persisted (an HMAC of the username and a timestamp, nothing else) and replayed at startup, so
  restarting the server does not reset a lockout.

`python -m app.cli create-invite --admin`, `create-invite [--max-uses N]`, `list-users`, `remove-user <username>`,

`verify-backup <archive>` (checks an archive completely without restoring it; exit 0 = good), `restore <archive>`,
`check-config` (effective non-secret settings and warnings; exit 1 on errors), `seed-dev`.

## End-to-end encryption keys (Signal protocol, see `SECURITY.md`)

Key formats are libsignal serializations, base64: identity and EC keys are 33-byte `ECPublicKey`,
PQ keys are `KEMPublicKey` (Kyber1024, 1569 bytes), signatures are 64 bytes.

`PUT /keys` (the calling device):
```json
{"registration_id": 1234,
 "identity_key": "b64",
 "signed_prekey": {"key_id": 1, "public_key": "b64", "signature": "b64"},
 "pq_last_resort_prekey": {"key_id": 1, "public_key": "b64", "signature": "b64"},
 "one_time_prekeys": [{"key_id": 2, "public_key": "b64"}],
 "one_time_pq_prekeys": [{"key_id": 2, "public_key": "b64", "signature": "b64"}]}
```
- `204`. The first upload must contain `registration_id`, `identity_key`, `signed_prekey` and
  `pq_last_resort_prekey`; later uploads may contain any subset (e.g. only fresh one-time keys or a rotated
  signed prekey). The identity key of a device can never change (`409 identity_key_mismatch`); a new identity
  means a new device. One-time keys with an existing `key_id` are ignored. At most 200 keys of each kind per
  request. Uploading keys emits `devices_changed` to everyone sharing a conversation with the user.
- The server does not verify signatures (it has no libsignal); clients verify them when building sessions.

`GET /keys/status` → `200 {"one_time_prekeys": 37, "one_time_pq_prekeys": 37, "signed_prekey_id": 1,
"pq_last_resort_prekey_id": 1}` for the calling device. Clients top up below 20.

`GET /keys/{user_id}` (optional `?device_id=uuid`) → `200`:
```json
{"user_id": "uuid", "devices": [
  {"device_id": "uuid", "device_number": 1, "registration_id": 1234, "identity_key": "b64",
   "signed_prekey": {"key_id": 1, "public_key": "b64", "signature": "b64"},
   "pq_prekey": {"key_id": 2, "public_key": "b64", "signature": "b64"},
   "one_time_prekey": {"key_id": 5, "public_key": "b64"}}]}
```
Each fetch consumes (deletes) one one-time EC prekey and one one-time PQ prekey per returned device, but only
for the first 10 fetches per hour by the same calling **user** for the same target device; later fetches in that
hour return the bundle without one-time keys (`one_time_prekey: null`, `pq_prekey` = last-resort key) and consume
nothing. Fetches are also limited to 120 per minute per calling user (`429`).
`one_time_prekey` is `null` when exhausted or rationed; `pq_prekey` falls back to the last-resort PQ key. Only active
devices that have uploaded keys are returned. The caller's own current device is never returned.

## Messages

`POST /messages`:
```json
{"id": "uuid", "conversation_id": "uuid", "kind": "message|edit|delete|reaction|call", "target_message_id": "uuid|null",
 "client_ts": 0, "attachment_ids": ["uuid"],
 "envelopes": [{"device_id": "uuid", "type": "prekey|whisper", "body": "b64"}]}
```
- The sender encrypts the content separately for **every active device of every current member, including
  the sender's own other devices, excluding the sending device**. The server checks that the envelope set
  matches exactly; otherwise `409`:
  `{"code": "mismatched_devices", "message": "...", "missing_devices": [{"user_id", "device_id"}],
  "extra_devices": [{"user_id", "device_id"}]}`. The client refreshes device lists/keys and retries with the
  same message `id`.
- `kind: "reaction"` needs `target_message_id` naming a non-deleted message of `kind: "message"` in the same
  conversation, **by any member** (not only the sender). It carries envelopes for the full device set like a
  message; the encrypted content holds the emoji and is bound to the target, the server never sees the emoji. No
  attachments. A reaction is not a message for the server: it does not change `last_message_at`/`last_message_seq`
  or unread counts. It is synchronised as an ordinary `message` event whose `data.kind` is `"reaction"` and is
  part of the history (`GET /conversations/{id}/messages`). Deleting the target drops undelivered reaction
  envelopes too (those events are then skipped). Old clients that do not know the kind ignore it. The server places
  no constraint on the encrypted content: the apps also send poll votes this way (content type `poll_vote`, see
  ARCHITECTURE.md "Content types and local-only data"), so the server cannot tell a vote from an emoji reaction.
- `kind: "call"` is the signalling channel for 1:1 audio/video calls (offer, answer, ICE candidates, hangup, busy;
  the encrypted content decides which). Only in `direct` conversations (`409 calls_direct_only` otherwise), no
  `target_message_id`, no attachments (`422`). It carries envelopes for the full device set like a message, so all
  of the callee's devices ring and the caller's other devices learn the outcome; the server never sees the SDP. Inside the
  encrypted content the `call` object is `{call_id, action, video, sdp?, candidates?, reason?, sent_at?}`; `sent_at` is the
  sender's clock in epoch milliseconds (always set by current clients, which drop an offer without it or more than 5 minutes
  from their own clock).
  It is **not a message** for the server: no `last_message_*`/`updated_at`/unread change, it ignores
  `disappearing_seconds`, is never in `GET /conversations/{id}/messages`, and cannot be edited, deleted or reacted
  to. It is synchronised as an ordinary `message` event with `data.kind: "call"`. Retention is short: the hourly
  maintenance job deletes call messages with their envelopes, delivered or not, once older than
  `SWAHNCHAT_CALL_RETENTION_SECONDS` (default 600), so a device that was offline gets the event but may see no
  content; clients must ignore call events whose `server_ts` is older than the call timeout (about a minute) rather
  than ring. At most 60 call messages per minute per sender (`429 rate_limited`). The push for it is content-free
  like any other (`{"t":"sync"}`) but is sent with high priority (see below). Old clients ignore the unknown kind.
- `kind: "edit"` and `kind: "delete"` need `target_message_id` naming a non-deleted message by the same sender
  in the same conversation. Both carry envelopes for the full device set, like a normal message: an edit holds
  the new encrypted content, a delete holds an encrypted `{"v":2,"type":"delete","conversation_id","message_id","target_message_id"}` content. Recipients apply a delete
  only after decrypting it, so the server cannot forge one. The server marks the target deleted and drops its
  undelivered ciphertexts. Deletes carry no attachments.
- `attachment_ids` must be `message` attachments uploaded by the sender. Members of the conversation may then
  download them.
- Idempotency: the message `id` is the idempotency key. Re-sending an `id` already stored for the same sender
  returns `200 {"message": Message, "duplicate": true}` without creating events. An `id` used by another
  sender returns `409 id_conflict`. A new message returns `201 {"message": Message, "duplicate": false}`
  (the returned `envelope` is `null`).
- Disappearing messages (server side): when the conversation has `disappearing_seconds` at the moment a message of
  any kind is stored, the message gets `expires_at = server_ts + disappearing_seconds * 1000` (fixed at insert;
  later timer changes do not touch it). The hourly maintenance job deletes expired messages with their envelopes,
  attachment links and receipts, together with edits and reactions that name them; attachments nothing references
  any more are then removed by the usual garbage collection. **Clients must not delete local history because of
  these fields**: the timer also travels as encrypted content between the phones, and only that is trusted
  (SECURITY.md). The server column limits how long ciphertext stays on the server.
- Limits: each envelope body ≤ 64 KiB decoded, ≤ 1000 envelopes, ≤ 10 attachments.

## Calls

`GET /calls/turn` (authenticated, 30 per minute per user) → short-lived TURN credentials per the TURN REST API
(coturn `use-auth-secret`):
```json
{"urls": ["stun:pi.example.ts.net:3478", "turn:pi.example.ts.net:3478?transport=udp"],
 "username": "1767225600:<user_id>", "credential": "<base64 HMAC-SHA1(secret, username)>", "ttl": 3600}
```
`username` is `<expiry unix seconds>:<user_id>`; use them as the `iceServers` entry. Without `SWAHNCHAT_TURN_URLS`
there is no relay: `urls` holds only the optional STUN URLs (`SWAHNCHAT_STUN_URLS`, possibly empty) and
`username` and `credential` are `null`, so clients still try direct (host) candidates. Fetch fresh credentials per
call. Setup: RASPBERRY_PI_SETUP.md, section 12.

Push for calls: a `call` message makes the server push immediately like any message, with the same content-free body
`{"t":"sync"}`, plus the request headers `Priority: 5` (ntfy: max/urgent) and `Urgency: high` (RFC 8030, for
distributors that honour it). Nothing about the call is in the body.

## Synchronisation

Every device has its own event queue on the server. History and delivery never depend on an open WebSocket:
the WebSocket only says "there is something new".

`GET /sync?after=<cursor>&limit=<1..500, default 200>` →
`200 {"events": [Event], "next_cursor": 123, "has_more": false}`. A new device starts at `after=0` and only
receives events created after the device was registered (use `GET /conversations` for the current state).

```jsonc
// Event
{"seq": 123, "type": "...", "created_at": 0, "conversation_id": "uuid|null", "data": {}}
```

| `type` | `data` |
|---|---|
| `message` | `Message` with this device's envelope (also used for edits, deletes, reactions and call signals: see `data.kind`) |
| `receipt` | `{"conversation_id", "user_id", "type": "delivered", "message_ids": [...]}` or `{"conversation_id", "user_id", "type": "read", "up_to_seq": 0}`. Receipts a device has not acknowledged yet are coalesced: per (conversation, user, type) the device has at most one queued `read` receipt (the highest `up_to_seq`) and one `delivered` receipt (all `message_ids`). The merged receipt gets a new, higher event `seq`, so a device that already fetched an older one receives it again on its next sync (process it idempotently, as always). Clients show the event's `created_at` as the delivered/read time, so a merged receipt carries the time of the merge |
| `conversation_updated` | `Conversation` (created, renamed, avatar, members or roles changed) |
| `conversation_removed` | `{"conversation_id"}` — the user left or was removed |
| `devices_changed` | `{"user_id"}` — a user you share a conversation with added/removed a device or keys |
| `user_updated` | `User` |
| `user_removed` | `{"user_id"}` |

`POST /sync/ack {"cursor": 123}` → `204`. Confirms that the device processed all events up to `cursor`.
The server then marks the message envelopes in those events as delivered and emits one `delivered` receipt per
(message, recipient user) to the sender's devices (merged with delivered receipts still waiting there, see `receipt`). Clients must process events idempotently: the same event
can be returned again until it is acknowledged.

## WebSocket `/ws`

Authenticate with `Authorization: Bearer <token>` (or `?access_token=` where headers are impossible).
An invalid or expired token closes the socket with code `4401`; the client refreshes and reconnects.
When the server shuts down or restarts it closes every socket with code `1001` ("server restarting"): reconnect
right away (with the usual backoff if the server is not back yet), then `GET /sync`.

Server → client:
- `{"type": "hello", "cursor": 123}` — latest event seq for this device; sync if newer than local cursor.
- `{"type": "sync", "cursor": 124}` — new events exist; call `GET /sync`.
- `{"type": "typing", "conversation_id": "uuid", "user_id": "uuid", "state": "start|stop"}`
- `{"type": "pong"}`
- `{"type": "presence", "user_id": "uuid", "online": true, "last_seen_at": 1700000000000}` — only about users who
  opted in (`PATCH /users/me/settings`) and share a conversation with you; sent when their first device connects or
  their last device disconnects (debounced: the first change goes out at once, later changes of the same user at
  most every 10 s, `SWAHNCHAT_PRESENCE_DEBOUNCE_SECONDS`, and only the state current at that moment). Nothing is
  sent for users who did not opt in. When someone switches sharing off, one final frame with `online: false` and
  `last_seen_at: null` tells you to forget what you showed (the same as for any user who does not share). On
  connect there is no snapshot: read `GET /users`. Clients that do not know this type ignore it.

Client → server:
- `{"type": "typing", "conversation_id": "uuid", "state": "start|stop"}` (relayed to the other members'
  connected devices, never stored)
- `{"type": "ping"}`

The server sends a WebSocket ping every 25 s and drops connections that do not answer within 60 s.

Limits: frames larger than 64 KiB are rejected; more than 100 inbound frames in 10 s (valid or not) close the
socket with `1008`; beyond 20 typing frames or 5 pings per 10 s the extra ones are silently ignored. A client
that does not read (more than 256 queued server messages) is closed with `1008`; nothing is lost, reconnect and
`GET /sync`. The server re-checks the session about every 60 s and closes with `4401` when the session, device
or user has been revoked or disabled (also when that happened through the server CLI); a socket outlives the
15 minute access token, only revocation ends it. Prefer the `Authorization` header: the query-string token is
redacted in server logs, but proxies and other logs may still record it.

## Attachments

`POST /attachments?purpose=message|avatar` with the raw bytes as the body (streamed).
- `purpose=message`: `Content-Type: application/octet-stream`. The body is the **client-encrypted** file; the
  server cannot inspect it. Max `SWAHNCHAT_MAX_ATTACHMENT_MB` (default 100).
- `purpose=avatar`: `Content-Type: image/jpeg|image/png|image/webp`, max 2 MiB, magic bytes must match the
  type. Avatars are not end-to-end encrypted (they are visible to all users of the server).
- Optional header `X-Content-SHA256: <hex>`; the server rejects the upload with `422 checksum_mismatch` if the
  received bytes differ.
- Per-user quota `SWAHNCHAT_USER_QUOTA_MB` (default 2048) → `413 quota_exceeded`.
- `201 {"id", "purpose", "content_type", "size", "sha256", "created_at"}`.

### Resumable uploads (large message attachments)

For files too big to risk on one request. Quota for the whole `size` is reserved when the session starts
(`POST /attachments` sees the reservation too). Existing `POST /attachments` is unchanged.

| Method | Path | Body | Result |
|---|---|---|---|
| POST | `/attachments/uploads` | `{size: 1.., purpose: "message", sha256?: hex}` | `201 {upload_id, offset: 0, size, expires_at, max_chunk_bytes}`. `413 payload_too_large` above `SWAHNCHAT_MAX_ATTACHMENT_MB`, `413 quota_exceeded`, `429 too_many_uploads` (10 open sessions per user), `429 rate_limited` |
| PATCH | `/attachments/uploads/{id}` | raw bytes, `Content-Type: application/octet-stream`, header `Upload-Offset: <current offset>` | `200 {offset}` (also as header `Upload-Offset`), or `201` with the attachment object after the last byte. At most 8 MiB per request and not beyond `size` (`413 payload_too_large`). `409 offset_mismatch` (body `{"offset": n}` and header `Upload-Offset` name the server's offset), `409 upload_busy` when another chunk of the session is being written, `409 upload_corrupt` if the stored file no longer matches the session (the session is dropped; start again), `422 invalid_request` (missing or bad header, empty chunk), `415`. A request that breaks off leaves no trace: resume at the reported offset |
| GET / HEAD | `/attachments/uploads/{id}` | – | `200 {upload_id, offset, size, expires_at, max_chunk_bytes}` with headers `Upload-Offset` and `Upload-Length` (HEAD: headers only). Use it to find where to continue |

When `offset == size` the server checks `sha256` (if given; `422 checksum_mismatch` ends the session, start over)
and turns the file into an ordinary attachment: the `201` body is the same object `POST /attachments` returns and
**its `id` equals the `upload_id`**, so a client that lost the response can still use `GET /attachments/{upload_id}`.
Only the creator can see or change a session (everyone else, unknown ids and expired sessions get `404`). Sessions
expire 24 hours after they start; the hourly job deletes expired sessions and their temp files and the reserved
quota is free again. Finished attachments follow the usual rule (deleted after 24 h unless a message uses them).

`GET /attachments/{id}` → the bytes, with `Range` support (`206`) for resumed downloads. Allowed for the
uploader, for members of a conversation containing a non-deleted message that references the attachment, and
for any authenticated user for avatars. Everyone else gets `404`. Unreferenced message attachments are deleted
after 24 h, and so are avatars that no user and no conversation uses any more (for example the previous avatar
after a change), by the hourly maintenance job.
