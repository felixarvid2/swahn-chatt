# FamilyChat API (v1)

This document is the contract between the backend (`backend/`) and the Android client (`android/`).
The running server also serves a generated OpenAPI document at `/api/v1/openapi.json` and Swagger UI at
`/api/v1/docs` (disabled when `FAMILYCHAT_ENV=production` unless `FAMILYCHAT_EXPOSE_DOCS=true`).

## Conventions

- Base path: `/api/v1`. JSON bodies are UTF-8, `snake_case`.
- IDs are UUIDv4 strings (lowercase, with dashes). Message IDs are generated by the client.
- Times are integers: **milliseconds since the Unix epoch, UTC** (`*_at`, `*_ts` fields).
- Binary values in JSON (keys, ciphertext) are **standard base64 with padding**.
- Authentication: `Authorization: Bearer <access_token>` on every endpoint except `/auth/*` (other than
  logout), `/healthz` and `/readyz`.
- Errors: non-2xx responses have the body `{"code": "<machine_code>", "message": "<human text>"}`, sometimes
  with extra fields (documented per endpoint). Common codes:
  `invalid_request` (422), `unauthorized` (401), `token_expired` (401), `forbidden` (403), `not_found` (404),
  `conflict` (409), `rate_limited` (429, with a `Retry-After` header in seconds), `payload_too_large` (413),
  `quota_exceeded` (413), `unsupported_media_type` (415).
- Ordering: `seq` values are integers assigned by the server from one monotonic counter. Message `seq` orders
  messages; event `seq` is the sync cursor. They are different counters.

## Objects

```jsonc
// User
{"id": "uuid", "username": "anna", "display_name": "Anna", "avatar_attachment_id": "uuid|null",
 "is_admin": false, "created_at": 1700000000000}

// Device
{"id": "uuid", "user_id": "uuid", "number": 1, "name": "Pixel 8", "created_at": 0, "last_seen_at": 0,
 "identity_key": "base64|null"}   // identity_key is null until the device uploaded keys

// Conversation
{"id": "uuid", "type": "direct|group", "name": "string|null", "avatar_attachment_id": "uuid|null",
 "created_by": "uuid", "created_at": 0, "updated_at": 0, "last_message_at": 0 /*or null*/,
 "last_message_seq": 0 /*or null*/, "my_read_seq": 0, "unread_count": 0,
 "members": [{"user_id": "uuid", "role": "admin|member", "joined_at": 0}]}

// Envelope: one ciphertext addressed to one device
{"device_id": "uuid", "type": "prekey|whisper", "body": "base64"}

// Message (as returned to one device; `envelope` is that device's ciphertext, or null)
{"id": "uuid", "conversation_id": "uuid", "sender_user_id": "uuid", "sender_device_id": "uuid",
 "kind": "message|edit|delete", "target_message_id": "uuid|null", "client_ts": 0, "server_ts": 0,
 "seq": 0, "attachment_ids": ["uuid"], "deleted": false,
 "envelope": {"type": "prekey|whisper", "body": "base64"}}
```

`direct` conversations have exactly two members and `name: null`; the client shows the other person's name.

Clients identify devices by `id`. `Device.number` and `device_number` in key bundles are informational only.
All sender, conversation and target fields on message events are claims that clients check against the decrypted
content (see SECURITY.md, "Content is bound to its context").

## Authentication

Accounts exist only through invitations made by an administrator. There is no open signup.

Username: `^[a-z0-9_.-]{3,32}$` (the server lowercases input). Password: 10–256 characters.
Display name: 1–64 characters. Device name: 1–64 characters.

`AuthResponse`:
```json
{"access_token": "jwt", "access_expires_at": 0, "refresh_token": "opaque", "refresh_expires_at": 0,
 "user": {"...User"}, "device": {"...Device"}}
```

| Method | Path | Body | Result |
|---|---|---|---|
| POST | `/auth/invite/redeem` | `{code, username, password, display_name, device_name}` | `201 AuthResponse`. `404 invalid_invite` for unknown/expired/used codes, `409 username_taken` |
| POST | `/auth/login` | `{username, password, device_name}` | `200 AuthResponse`. Every login registers a **new device**. `401 invalid_credentials` (same answer for unknown user and wrong password). `409 device_limit` when the account already has the maximum number of active devices (default 10, `FAMILYCHAT_MAX_DEVICES_PER_USER`; the `message` says so: remove a device, then log in again). `429 rate_limited` while the username is locked after repeated failures (see below) |
| POST | `/auth/refresh` | `{refresh_token}` | `200 AuthResponse` with a **new** refresh token; the old one stops working. Presenting **any** refresh token the session issued earlier (not only the previous one) revokes the whole session and its device (`401 token_reused`) |
| POST | `/auth/logout` | – (auth) | `204`. Revokes the session and the device, deletes the device's public keys |

- Access tokens are JWT (HS256) valid for 15 minutes (`FAMILYCHAT_ACCESS_TOKEN_MINUTES`). Refresh tokens are
  random 256-bit values, stored hashed, valid for 60 days (`FAMILYCHAT_REFRESH_TOKEN_DAYS`), sliding on refresh.
- Each request re-checks that the session, device and user are still active, so revocation is immediate.
- An expired access token returns `401 {"code":"token_expired"}`; the client refreshes and retries once.
- Rate limits (in-process): per client IP (IPv6 clients per /64 prefix) login 10/min and 5/min per IP+username,
  redeem 10/min, refresh 30/min; key-bundle fetches 120/min per user. Exceeding returns `429` with `Retry-After`.
- Per-username lockout: after 10 failed logins within an hour (or 30 within a day) for a username, from any
  addresses, further logins for that username get `429 rate_limited` (with `Retry-After`) until the failures age
  out, even with the right password. Unknown usernames behave identically. Signed-in devices are not affected.

## End-to-end encryption keys (Signal protocol, see `SECURITY.md`)

Key formats are libsignal serializations, base64: identity and EC keys are 33-byte `ECPublicKey`,
PQ keys are `KEMPublicKey` (Kyber1024, 1569 bytes), signatures are 64 bytes.

`PUT /keys` (the calling device):
```json
{"registration_id": 1234,
 "identity_key": "b64",
 "signed_prekey": {"key_id": 1, "public_key": "b64", "signature": "b64"},
 "pq_last_resort_prekey": {"key_id": 1, "public_key": "b64", "signature": "b64"},
 "one_time_prekeys": [{"key_id": 2, "public_key": "b64"}],
 "one_time_pq_prekeys": [{"key_id": 2, "public_key": "b64", "signature": "b64"}]}
```
- `204`. The first upload must contain `registration_id`, `identity_key`, `signed_prekey` and
  `pq_last_resort_prekey`; later uploads may contain any subset (e.g. only fresh one-time keys or a rotated
  signed prekey). The identity key of a device can never change (`409 identity_key_mismatch`); a new identity
  means a new device. One-time keys with an existing `key_id` are ignored. At most 200 keys of each kind per
  request. Uploading keys emits `devices_changed` to everyone sharing a conversation with the user.
- The server does not verify signatures (it has no libsignal); clients verify them when building sessions.

`GET /keys/status` → `200 {"one_time_prekeys": 37, "one_time_pq_prekeys": 37, "signed_prekey_id": 1,
"pq_last_resort_prekey_id": 1}` for the calling device. Clients top up below 20.

`GET /keys/{user_id}` (optional `?device_id=uuid`) → `200`:
```json
{"user_id": "uuid", "devices": [
  {"device_id": "uuid", "device_number": 1, "registration_id": 1234, "identity_key": "b64",
   "signed_prekey": {"key_id": 1, "public_key": "b64", "signature": "b64"},
   "pq_prekey": {"key_id": 2, "public_key": "b64", "signature": "b64"},
   "one_time_prekey": {"key_id": 5, "public_key": "b64"}}]}
```
Each fetch consumes (deletes) one one-time EC prekey and one one-time PQ prekey per returned device, but only
for the first 10 fetches per hour by the same calling **user** for the same target device; later fetches in that
hour return the bundle without one-time keys (`one_time_prekey: null`, `pq_prekey` = last-resort key) and consume
nothing. Fetches are also limited to 120 per minute per calling user (`429`).
`one_time_prekey` is `null` when exhausted or rationed; `pq_prekey` falls back to the last-resort PQ key. Only active
devices that have uploaded keys are returned. The caller's own current device is never returned.

## Messages

`POST /messages`:
```json
{"id": "uuid", "conversation_id": "uuid", "kind": "message|edit|delete", "target_message_id": "uuid|null",
 "client_ts": 0, "attachment_ids": ["uuid"],
 "envelopes": [{"device_id": "uuid", "type": "prekey|whisper", "body": "b64"}]}
```
- The sender encrypts the content separately for **every active device of every current member, including
  the sender's own other devices, excluding the sending device**. The server checks that the envelope set
  matches exactly; otherwise `409`:
  `{"code": "mismatched_devices", "message": "...", "missing_devices": [{"user_id", "device_id"}],
  "extra_devices": [{"user_id", "device_id"}]}`. The client refreshes device lists/keys and retries with the
  same message `id`.
- `kind: "edit"` and `kind: "delete"` need `target_message_id` naming a non-deleted message by the same sender
  in the same conversation. Both carry envelopes for the full device set, like a normal message: an edit holds
  the new encrypted content, a delete holds an encrypted `{"v":2,"type":"delete","conversation_id","message_id","target_message_id"}` content. Recipients apply a delete
  only after decrypting it, so the server cannot forge one. The server marks the target deleted and drops its
  undelivered ciphertexts. Deletes carry no attachments.
- `attachment_ids` must be `message` attachments uploaded by the sender. Members of the conversation may then
  download them.
- Idempotency: the message `id` is the idempotency key. Re-sending an `id` already stored for the same sender
  returns `200 {"message": Message, "duplicate": true}` without creating events. An `id` used by another
  sender returns `409 id_conflict`. A new message returns `201 {"message": Message, "duplicate": false}`
  (the returned `envelope` is `null`).
- Limits: each envelope body ≤ 64 KiB decoded, ≤ 1000 envelopes, ≤ 10 attachments.

## Synchronisation

Every device has its own event queue on the server. History and delivery never depend on an open WebSocket:
the WebSocket only says "there is something new".

`GET /sync?after=<cursor>&limit=<1..500, default 200>` →
`200 {"events": [Event], "next_cursor": 123, "has_more": false}`. A new device starts at `after=0` and only
receives events created after the device was registered (use `GET /conversations` for the current state).

```jsonc
// Event
{"seq": 123, "type": "...", "created_at": 0, "conversation_id": "uuid|null", "data": {}}
```

| `type` | `data` |
|---|---|
| `message` | `Message` with this device's envelope (also used for edits and deletes) |
| `receipt` | `{"conversation_id", "user_id", "type": "delivered", "message_ids": [...]}` or `{"conversation_id", "user_id", "type": "read", "up_to_seq": 0}` |
| `conversation_updated` | `Conversation` (created, renamed, avatar, members or roles changed) |
| `conversation_removed` | `{"conversation_id"}` — the user left or was removed |
| `devices_changed` | `{"user_id"}` — a user you share a conversation with added/removed a device or keys |
| `user_updated` | `User` |
| `user_removed` | `{"user_id"}` |

`POST /sync/ack {"cursor": 123}` → `204`. Confirms that the device processed all events up to `cursor`.
The server then marks the message envelopes in those events as delivered and emits one `delivered` receipt per
(message, recipient user) to the sender's devices. Clients must process events idempotently: the same event
can be returned again until it is acknowledged.

## WebSocket `/ws`

Authenticate with `Authorization: Bearer <token>` (or `?access_token=` where headers are impossible).
An invalid or expired token closes the socket with code `4401`; the client refreshes and reconnects.
When the server shuts down or restarts it closes every socket with code `1001` ("server restarting"): reconnect
right away (with the usual backoff if the server is not back yet), then `GET /sync`.

Server → client:
- `{"type": "hello", "cursor": 123}` — latest event seq for this device; sync if newer than local cursor.
- `{"type": "sync", "cursor": 124}` — new events exist; call `GET /sync`.
- `{"type": "typing", "conversation_id": "uuid", "user_id": "uuid", "state": "start|stop"}`
- `{"type": "pong"}`

Client → server:
- `{"type": "typing", "conversation_id": "uuid", "state": "start|stop"}` (relayed to the other members'
  connected devices, never stored)
- `{"type": "ping"}`

The server sends a WebSocket ping every 25 s and drops connections that do not answer within 60 s.

Limits: frames larger than 64 KiB are rejected; more than 100 inbound frames in 10 s (valid or not) close the
socket with `1008`; beyond 20 typing frames or 5 pings per 10 s the extra ones are silently ignored. A client
that does not read (more than 256 queued server messages) is closed with `1008`; nothing is lost, reconnect and
`GET /sync`. The server re-checks the session about every 60 s and closes with `4401` when the session, device
or user has been revoked or disabled (also when that happened through the server CLI); a socket outlives the
15 minute access token, only revocation ends it. Prefer the `Authorization` header: the query-string token is
redacted in server logs, but proxies and other logs may still record it.

## Attachments

`POST /attachments?purpose=message|avatar` with the raw bytes as the body (streamed).
- `purpose=message`: `Content-Type: application/octet-stream`. The body is the **client-encrypted** file; the
  server cannot inspect it. Max `FAMILYCHAT_MAX_ATTACHMENT_MB` (default 100).
- `purpose=avatar`: `Content-Type: image/jpeg|image/png|image/webp`, max 2 MiB, magic bytes must match the
  type. Avatars are not end-to-end encrypted (they are visible to all users of the server).
- Optional header `X-Content-SHA256: <hex>`; the server rejects the upload with `422 checksum_mismatch` if the
  received bytes differ.
- Per-user quota `FAMILYCHAT_USER_QUOTA_MB` (default 2048) → `413 quota_exceeded`.
- `201 {"id", "purpose", "content_type", "size", "sha256", "created_at"}`.

`GET /attachments/{id}` → the bytes, with `Range` support (`206`) for resumed downloads. Allowed for the
uploader, for members of a conversation containing a non-deleted message that references the attachment, and
for any authenticated user for avatars. Everyone else gets `404`. Unreferenced message attachments are deleted
after 24 h.
